dshaptics 설정 구조

현재 json 인터페이스와 입력값, 그리고 새 기능(좌우·트리거·라이트바·상태 베드)을 넣었을 때의 모습. 2026-10-06 기준 코드에서 읽음.

먼저 사실관계. "json만 고친다"는 원칙은 지금 P의 거짓(UE4 공용 경로)에만 적용돼 있어요. 오공은 대부분이 dshaptics.py 안의 상수와 정규식 표예요. json은 도구가 만든 데이터(음원 트리·자동 분류)뿐이에요.

그리고 복잡도는 생각보다 작게 잡을 수 있어요. 사람이 자주 만지는 곳은 규칙(rules) 한 줄뿐이고, 새 기능은 그 한 줄에 선택 필드로 붙이면 돼요.

1. P의 거짓 — profiles/liesofp/haptics.json

최상위 섹션 9개. 누가 언제 만지는지로 나누면 이렇습니다.

자동 도구가 채움, 사람은 안 봄   가끔 게임당 한 번 정함   자주 튜닝할 때 계속 만짐

섹션빈도하는 일입력값 (현재)
exe가끔실행 중인 게임과 이 파일을 연결"LOP-Win64-Shipping.exe"
native자동DLL이 훅 걸 주소. tools/find_ue4_audio.py 출력을 붙임AddNewActiveSound 패턴++3be3ae0, FNameToString, SoundOffset 18, OwnerNameOffset 44
player가끔"내 소리" 판별 정규식 (owner·소리 이름)"PC_Pino|_PC_"
master / duck자주전체 세기 / 큰 진동 밑에 깔린 작은 진동을 줄이는 비율0.6 / 0.3
waves가끔진동 파형 사전. 이름 → 파형 조각 목록19종 (pguard, guard, struck, fatal, impact, swing, charge, dodge, heal, ergo, step, thud, break, seq, down, tick, arm, land, splash)
rules자주소리 이름 → 어떤 파형. 위에서부터 첫 일치18줄
my_hit가끔내 타격 전용 소리가 없는 게임용 대체 규칙 (휘두른 직후 적 피격음)null (P의 거짓은 SE_PC_SK_Hit_*가 있어서 불필요)
combat_hold / gap가끔전투 상태 유지 시간 / 같은 파형 최소 간격6.0초 / 0.05초
weather가끔비 그래뉼러 + 천둥 럼블 생성기아래 표
cutscene가끔컷씬 중엔 충격 소리만 은은하게max_s 300, match 충격 단어 정규식, wave seq, gap 0.12

waves — 파형 문법

"pguard": [[260, 18, 1.0, 5], [150, 25, 0.8, 8], [70, 130, 0.75, 55]],
"charge": [[100, 30, 0.4, 12], 45, [100, 35, 0.55, 14]],
"heal":   [{"swell": [70, 600, 0.35]}]

[주파수 Hz, 길이 ms, 세기, 감쇠 ms]  = 짧은 타격 하나
숫자 하나                            = 쉼 (ms)
{"swell": [주파수, 길이, 세기]}       = 부풀었다 꺼지는 진동

rules — 규칙 한 줄의 필드

{"match": "^SE_PC_MT_Rustle_Attack_Charge", "wave": "charge", "who": "any", "player_control": true}
필드필수뜻
match필수소리 이름 정규식
wave필수waves 사전의 이름
who선택생략하면 내 소리일 때만. "any"면 주체 무관
combat선택이 소리가 나면 전투 상태로 표시
combat_only선택전투 상태일 때만 울림 (발소리)
player_control선택이 소리가 나면 컷씬이 끝난 것으로 봄
swing선택my_hit 대체 규칙용 "방금 휘둘렀음" 표시

weather — 비·천둥

필드입력값뜻
on^AMB_SS_Rain|^AMB_OS_Thunder이 소리가 나면 날씨 켜짐
layer^AMB_SS_Rain_(\w+?)_Set괄호 부분 = 지금 비 맞는 재질 (PC=몸, Wood/Metal=지붕)
hold / rate / peak45 / 14 / 0.2유지 초 / 초당 빗방울 / 최대 세기
grainsPC, Wood(gain 0.25), Metal(gain 0.25, ring)재질별 빗방울 파형
rumbleThunder, gap 18, chance 0.5, peak 0.35천둥 럼블

2. 오공 — 코드 안에 있는 것들

dshaptics.py 안 (사람이 고치는 값)

  • W 합성 파형 19종
  • RULES 정규식 21줄 (이벤트 → 파형)
  • HAPTIC_TRIM 7줄 / SPEAKER_TRIM / STOPS
  • SPEAKER_ALLOW 패드 스피커 허용 목록
  • 세기 상수: HAPTIC_MASTER 0.6, DUCK 0.3, SFX_GAIN 0.2, STEP_PEAK 0.18, SEQ_GAIN 2.0, ENV_GAIN 0.7 …
  • 트리거: TRIG_SPIN_AMP 2, TRIG_SPIN_HZ 12, TRIG_SPIN_HOLD 0.4
  • 내 타격 판정: HIT_PROXY, MY_ATTACK, PUNCH, HIT_WINDOW 0.8

json (도구가 만든 데이터)

  • rules_auto.json — LLM 분류 결과. 이벤트마다 class·weight·gain·snap
  • sonmat-maker/profiles/wukong_auto/glossary.txt · overrides.json — 분류기 힌트와 수동 덮어쓰기
  • trees.json · trees_seq.json — 이벤트 → 원본 음원 트리 (소리 준비가 만듦)
  • layers_step_switch.json — 바닥별 발소리 (소리 준비가 만듦)

사람이 튜닝하는 값은 거의 다 왼쪽에 있어요.

즉 오공은 아직 "게임별 코드"예요. 배포 원칙(json만 공유)을 지키려면 언젠가 P의 거짓과 같은 스키마로 옮겨야 해요. 옮길 때 새로 생기는 건 Wwise 쪽 입력(이벤트 이름·Switch) 정도고, 규칙 구조는 그대로 써요.

3. 새 기능을 넣으면 — 규칙 한 줄에 선택 필드

원칙: json은 "어떤 이벤트에 무엇을"만, "어떻게 만드는지"는 코드(공용 엔진)가 가져요. 새 기능마다 사전 하나 + 규칙 필드 하나씩만 늘어나요.

지금

{"match": "^SE_PC_MT_Arm_Flamberge", "wave": "arm", "who": "any", "combat": true}

추가 후 (전부 선택, 안 쓰면 지금과 똑같이 동작)

{"match": "^SE_PC_MT_Arm_Flamberge", "wave": "arm", "who": "any", "combat": true,
 "pan": -0.7,                    // -1 왼손 … 0 양손 … +1 오른손
 "trigger": {"L2": "flame"},     // triggers 사전 이름. 다음 변경 전까지 유지
 "light": "flame"}                // lights 사전 이름

새로 생기는 사전 (waves 와 같은 방식)

"triggers": {
  "flame":  {"mode": "vibrate", "amp": 2, "hz": 20},
  "grab":   {"mode": "resist",  "start": 3, "force": 120},
  "charge": {"mode": "weapon",  "start": 2, "end": 7, "force": 200},
  "off":    {"mode": "off"}
},
"lights": {
  "flame":  {"rgb": [255, 80, 20]},
  "lowhp":  {"rgb": [200, 0, 0], "pulse": 1.2}
},
"beds": {                         // weather 를 일반화. 비·바람·물속 같은 지속 질감
  "rain": { …지금 weather 내용 그대로… }
}
기능json 에 늘어나는 것코드에 늘어나는 것
좌우 pan규칙 필드 pan 1개믹서가 ch3·ch4에 다른 세기를 곱함 (몇 줄)
트리거triggers 사전 + 규칙 필드 trigger오공의 trig_vibrate/trig_resist를 공용으로 옮김 + 무기모드 추가
라이트바lights 사전 + 규칙 필드 light트리거와 같은 HID 출력 리포트에 RGB 3바이트
상태 베드weather → beds 이름만 일반화지금 비 생성기를 여러 개 돌릴 수 있게
맞은 방향없음 (자동)DLL이 위치를 같이 보냄. 엔진별 1회

복잡도 정리

  • 사람이 평소에 만지는 곳: rules 한 줄과 master/duck. 지금과 같아요.
  • 게임당 한 번: player, 사전 3~4개(waves·triggers·lights·beds). 대부분 다른 게임 것을 복사해서 이름만 바꾸면 돼요.
  • 자동: native.
  • 위험 신호: 규칙에 조건 필드(if, 상태 비교 같은 것)가 생기기 시작하면 json이 프로그래밍 언어가 돼요. 그 선은 넘지 않고, 그런 판정은 공용 코드의 이름 붙은 옵션(combat_only 같은)으로만 넣어요.
